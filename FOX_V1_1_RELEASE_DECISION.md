# Fox v1.1 Release Decision & Gate Review

## 1. Official Release Decision

### Verdict: REVISE V1.1

**Fox v1.1 must NOT be released in its current state. It must be revised before shipping.**

This decision is supported by empirical findings across 12 live autonomous coding agent trials, an independent 12-point adversarial evaluation suite, and runtime performance profiling against real open-source repositories (`pydantic/pydantic` and `astral-sh/setup-uv`).

---

## 2. Decision Rationale & Empirical Justification

### Why "Release v1.1" Was Rejected

In initial benchmarking on Pydantic #12884, Fox v1.1 appeared to achieve a breakthrough, reporting a 66.7% strict acceptance pass rate (2/3 passed) compared to 0% for Baseline and 0% for Fox v1.0.

However, phase 2 and phase 3 audits revealed that this success was superficial:
1. **Adversarial Failure Rate (91.7%)**: When tested against our 12-point independent adversarial acceptance suite (`HARNESS/fixtures/task1_adversarial_suite.py`), the patches generated by Fox v1.1 failed **11 out of 12 tests**.
2. **False Layer Modification**: The root cause of Pydantic #12884 is located in `pydantic-core` (written in Rust). The Fox v1.1 agents did not patch the core serializer; instead, they constructed an elaborate 90-line Python preprocessor in `pydantic/main.py` that cloned model graphs before passing them to Rust.
3. **Primary Entrypoint Bypass**: When models were serialized through Pydantic's official `TypeAdapter.dump_python()` or `TypeAdapter.dump_json()`, the Python preprocessor was completely bypassed, and data corruption persisted unchanged.
4. **Duplicate JSON Keys Unresolved**: In `model.model_dump_json()`, the Rust string writer continued emitting duplicate JSON keys (`{"x":10,"x":20}`).
5. **Collection Blind Spot**: The preprocessor failed to inspect models nested inside lists, tuples, or dictionary values, failing adversarial test T2 while creating the illusion of performance neutrality.

Releasing a reliability skill whose flagship patch fails 91.7% of adversarial checks would violate our engineering standards and erode user trust.

### Why "Keep v1.0" Was Rejected

Fox v1.0 demonstrated clear structural flaws during controlled benchmarking:
1. **Zero Diagnostic Value on Complex Boundaries**: On Task 1, Fox v1.0 achieved an identical 0% pass rate to Baseline, failing to guide the agent to any architectural insights.
2. **Severe Ceremonial Inflation**: On Task 5 (Setup-uv #1028), Fox v1.0 increased wall-clock execution time by **+103%** (80.25s vs 39.46s) and token consumption by **+60%** (34,471 vs 21,568) solely due to reciting formal stage transitions.
3. **Context Window Waste**: The 1,226-word root prompt contained inlined CLI contracts for optional scripts (`proof.py`, `scaffold.py`, `audit.py`) that wasted prompt budget on routine bug fixing.

### Why "Redesign Fox" Was Rejected

Fox v1.1 made genuine, measurable progress that should be preserved and refined:
1. **Validated Four-Step Model**: Replacing six rigid stages with Ground, Trace, Change, Verify eliminated ceremonial recitation, cutting Task 5 execution time by 26.1% and tokens by 7.6% relative to v1.0.
2. **Proven Boundary Discovery**: Baseline and Fox v1.0 agents never discovered that inner models bypassed top-level methods. Fox v1.1's architectural boundary tracing instructions directly caused the agent to identify the native engine traversal.
3. **Flawless Safety and Integrity**: Across all 12 live agent trials, unsupported claims and false test reports remained strictly at zero, and project regression test suites maintained 100% pass rates (121/121 Pydantic tests, 119/119 Setup-uv tests).

## 3. Systematic Answers to the Evaluation Questions

### 1. Did the successful Fox v1.1 patches survive adversarial testing?
**No.** Both passing patches (Trials 2 and 3) failed 11 out of 12 adversarial tests, surviving only the basic model immutability check. They failed on collections, recursive structures, custom serializers, computed fields, validation/serialization alias divergence, raw JSON duplicate keys, and TypeAdapter delegation.

### 2. Did they repair the correct implementation layer?
**No.** The underlying bug is in `pydantic-core` (Rust), where `to_python` and `to_json` iterate over extra fields and overwrite declared fields. The agent patched `pydantic/main.py` in Python with a pre-serialization cloning pass, leaving the core serializer uncorrected.

### 3. Did they introduce performance regressions?
**Minor on small models; algorithmic inefficiency on large models.** On flat models, latency differences were sub-millisecond (<0.001ms). However, on models with colliding extras, Trial 3 unconditionally performs deep graph traversal and dictionary copying in interpreted Python prior to native serialization, adding $O(V + E)$ redundant work.

### 4. Does v1.1 improve completion rates on unseen issues?
**Inconclusive pending external quota refresh.** Initial benchmark results showed a 75% pass rate (3/4) vs 25% for Baseline (1/4), but adversarial testing demonstrated that the Task 1 pass was incomplete. On Task 5, all conditions passed, with v1.1 running 26.1% faster than v1.0.

### 5. Is the improvement worth the additional tokens and time?
**Partially.** The reduction in word count (-62.7%) and removal of stage headings made v1.1 significantly leaner than v1.0. However, when an agent responds to boundary tracing by inventing multi-layer Python shims instead of addressing the core defect, token usage swells (up to 72,436 tokens in Trial 2) without producing a complete fix.

### 6. Which instructions contribute measurable value?
- **High value**: The Ground instruction (mandating executable reproducers) and the Trace instruction (identifying native/compiler boundaries).
- **High value**: Pruning optional tool contracts into progressive disclosure references.
- **Deficient**: The instruction to Trace lacked a critical corollary: **Layer Integrity**. The agent must be instructed to never wrap an engine defect with a language-level preprocessor shim, and to state clearly when a fix requires modifying an underlying native dependency.

### 7. Are any safety or reliability capabilities lost through simplification?
**No.** Truthful reporting, zero fabricated evidence, approval gating for destructive actions, and regression testing were 100% preserved in the 457-word v1.1 prompt.

## 4. Concrete Roadmap for Fox v1.2 Revision

To graduate Fox to release status, the following targeted revisions must be applied:

1. **Add Layer Integrity Invariant (Anti-Shim Rule)**:
   Explicitly instruct agents:
   > "Do not work around engine-level defects with surface preprocessors, recursive copying wrappers, or monkey-patches. If the defect exists in an underlying native extension, compiler, or external dependency, diagnose and address it in that layer, or document the boundary constraint rather than introducing intermediate shims."

2. **Expand the Verification Matrix for Alternate Entrypoints**:
   Update `skills/fox/references/validation.md` and the Verify step to require:
   - Testing alternative API entrypoints (e.g. `TypeAdapter` in addition to `BaseModel`).
   - Testing collection containers (lists, tuples, dicts).
   - Verifying raw wire formats (inspecting raw JSON strings for duplicate keys).

3. **Re-evaluate on the Unseen Tasks (#13074 and #13051)**:
   Once the OpenAI account quota resets, execute the frozen 18-trial benchmark to prove that the revised instructions guide agents to solve clean in-tree defects rapidly while handling native FFI boundaries with strict layer integrity.
