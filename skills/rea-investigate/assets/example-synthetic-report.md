## Architecture and boundaries

Zettlr structures its Electron architecture into three well-defined execution boundaries:

1. Renderer Process (Sandboxed UI):
   - Implemented with Vue 3, Pinia state stores, and CodeMirror editor components.
   - Executes inside Chromium with webPreferences sandbox: true and contextIsolation: true.
   - Contains no direct Node.js integration (no direct require, fs, or child_process access).
   - Relies exclusively on APIs injected into window by the preload script.

2. Preload Boundary (source/common/modules/preload/index.ts):
   - Executes in an isolated context between renderer and Electron runtime.
   - Calls contextBridge.exposeInMainWorld to expose window.ipc (invoke, send, sendSync, on), window.config, window.process metadata, and window.getPathForFile.
   - Implements listener cleanup closures to avoid memory leaks across window lifecycles.

3. Main Process (source/app/):
   - Powered by Node.js and Electron main APIs.
   - Uses an inversion-of-control container (AppServiceContainer) managing modular service providers:
     * CommandProvider: Listens on ipcMain.handle('application') and dispatches commands to registered ZettlrCommand classes.
     * ConfigProvider: Manages persistent JSON configuration and synchronizes preferences via IPC.
     * DocumentManager: Tracks open file buffers and modification states.
     * FSAL (File System Abstraction Layer): Handles directory descriptors and file reading.
     * WindowsProvider: Manages BrowserWindow lifecycles, chrome styles, and dialog modals.

## Adversarial audit

### Adversarial Review of Technical Claims

1. Claim: Export execution does not permit arbitrary remote shell code execution from renderer scripts.
   - Challenge: Does the 'custom-export' command allow untrusted renderer code to inject shell arguments?
   - Resolution: Verified secure. In source/app/service-providers/commands/export.ts#L60-L71, custom commands are looked up exclusively from the main process configuration (config.get().export.customCommands). The renderer only supplies a displayName string and target file. If the displayName does not match a pre-configured command, execution is rejected. Furthermore, the file argument is quoted before execution in runShellCommand.

2. Claim: Dirty buffer handling prevents data loss during export.
   - Challenge: If a user exports before saving, does the exported document contain stale disk content?
   - Resolution: Supported by code proof. In export.ts#L117-L123, isModified(file) triggers a write of current editor buffer memory to a temporary file in app.getPath('temp'), ensuring the exported file matches what the user sees in the editor.

3. Claim: Context isolation strictly prevents renderer access to Node.js APIs.
   - Challenge: Could a compromised renderer script bypass the bridge and access the main filesystem?
   - Resolution: Confirmed by Electron configuration. In create-main-window.ts#L52, sandbox: true and preload script ensure contextIsolation is active by default. The exposed bridge in preload/index.ts only exposes bounded IPC messaging methods without any Node.js module handles.

## Limitations and next experiments

Investigation limitations and environmental boundaries:

1. Static Repository Inspection:
   - Analysis was conducted on the cloned Git repository (commit 0d2839e) without running full electron-forge production bundling.
   - Dynamic IPC message interception in a live packaged Electron app requires DevTools or electron-devtools-installer, which was omitted in favor of static code analysis.

2. External Tool Dependency:
   - Single-file export strictly depends on Pandoc binary execution. In environments where Pandoc is not installed and no bundled binary is downloaded, export commands fail gracefully with an error modal.

3. Preload IPC Surface:
   - While contextIsolation and sandbox are enabled, window.ipc.invoke allows the renderer to pass arbitrary channel names to the main process. Security relies on main process command validation in CommandProvider.
